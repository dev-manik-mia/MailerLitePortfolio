01
A scalable solution inside an existing, mature codebase — and the debt tradeoff.
NOBS Marketplace · live since 2014 · Laravel, MySQL, Redis

NOBS is a wholesale SEO marketplace that has been taking real orders since 2014. When I picked it up, it carried everything a decade of shipping leaves behind: duplicated business logic, controllers doing four jobs each, and listing queries that got slower every time the catalogue grew.

The constraint was the interesting part. There was no maintenance window and no staging traffic that looked like production. Buyers and sellers were mid-transaction while I worked. Any change I made had to be reversible in a minute.

So I ruled out the rewrite immediately. A rewrite is a bet that you understand a system you demonstrably don't yet understand — you only find the undocumented rules by breaking them. I strangled it instead, in small pieces, measuring before and after each one.

Step 01
Measure, don't guess

Profiled the slow query log and request traces first. The bottleneck was never where the team assumed it was — it was N+1s inside a widely reused listing partial.

Step 02
Test the risk, then touch it

Characterisation tests around the money paths before a single line moved. Not for coverage numbers — so a refactor that changed behaviour failed loudly instead of quietly.

Step 03
Extract behind the old call sites

Duplicated logic moved into services while the original signatures kept working. Callers migrate one at a time; nothing needs a big-bang cutover.

Step 04
Move the waiting off the request

Anything the user didn't need to wait for went to a queue. Redis caching only where reads dominate and invalidation is a single, obvious event.

What I optimized
  • Eliminated N+1s and added deliberate eager loading on the hot listing paths
  • Rewrote the expensive catalogue queries and added the indexes to match
  • Redis caching on read-heavy data with a cheap, single-event invalidation
  • Pushed slow work into queues, with retries and backoff
  • Collapsed duplicated logic into services the whole team could reuse
What I deliberately didn't do
  • No rewrite. The business could not afford to pause for one
  • No raw SQL everywhere for a few percent — it would cost every future contributor
  • No bespoke caching layer only I could reason about six months later
  • No abstractions for scale the product hadn't reached yet
  • No change to a hot path that didn't have a test around it first

A 20% gain that one engineer understands is worse than a 15% gain the whole team can maintain. The second one is still there next year.

The result: measurably faster pages and a much lighter database, shipped incrementally, with no incident big enough to need a rollback. Just as important, the code the next person touches is smaller and better covered than the code I found.

Why I built it

Everything available was either a single-provider SDK or a Python-shaped port that ignored how Laravel works. I needed four things none of them gave me: swap a provider by changing config, run ingestion on Laravel's own queues, emit events I could observe in production, and fake the whole thing in tests.

So the contracts became the product. Seven interfaces; everything else is a driver behind them. Adding a provider is one class and a config block — including providers that didn't exist when I wrote it.

Framework · Go · net/http only

GoExpress ~500 LOC

A minimal web framework written from first principles on top of net/http: a prefix-tree router with :param and *wildcard segments, a middleware chain driven by c.Next(), nested route groups with group-scoped middleware, and a Context that owns params, JSON and status. Tests included.

trie routermiddleware chainroute groupsshort-circuitinggo test
admin := g.Group("/admin")
admin.Use(AdminGuard())

admin.DELETE("/users/:id", func(c *goexpress.Context) {
    c.JSON(http.StatusOK, map[string]string{
        "id": c.Param("id"),
    })
})
Why I built it

To stop treating routing as magic. I wanted to know exactly what happens when two routes collide, how a middleware short-circuits a request, and what a "group" actually is once you strip the sugar off.

I'll be straight about this one: I'd still ship Gin in production. The payoff wasn't the framework, it was that I now debug Laravel's router and middleware pipeline instead of guessing at them — which is exactly the skill a mature codebase asks for.

Why MailerLite, specifically.

I've built the small version of what you run: a sending engine with queue workers, SMTP rotation, throttling and bounce handling, inside a CRM with real customers on it. I know where it gets hard — the retry that double-sends, the suppression list that's stale by an hour, the worker that quietly dies at 3am.

You're operating that at a scale where those problems are permanent residents rather than incidents. That's the work I want, in a codebase mature enough that the interesting question is never "can we build it" but "can we change it without breaking anyone."
